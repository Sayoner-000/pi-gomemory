#### H-01 — La caché anterior oculta el pin aprobado por el binario actual

- **Categoría:** Integridad / error lógico.
- **Severidad:** Media.
- **Estado:** CONFIRMADO ADM y ACR.
- **Ubicación:** `pkg/installer/deps.go:349-395`, `DepsStatus` y `DepsStatusFor`.
- **Ruta de alcance:** CLI `deps-update` → `RunDepsUpdate` → `DepsStatusFor` → `DepsStatus`.
- **Análisis:** `DepsStatus` filtra por las versiones guardadas antes de que se consulten los probes actuales. `DepsStatusFor` sustituye comandos y relee `Current`, pero no sustituye el objetivo `Latest`. Con `current=latest=0.12.0` en caché y pin compilado `0.14.0`, la entrada desaparece antes de poder ofrecer la actualización. Los comandos no se inyectan desde caché; el defecto afecta a la elegibilidad/versión anunciada. No es una consulta npm fallida ni una autorización para instalar una versión no aprobada.
- **Evidencia:** `TestACRADM01NewPinOverridesOldCache`: `old cache hides new approved pin 0.14.0: got []`. No se ejecutó `pi install`.
- **Código corregido propuesto:** en `DepsStatusFor`, leer todas las entradas de `depsCache` antes del filtrado; dentro del recorrido, tras resolver el probe, aplicar este bloque y solo entonces `Outdated()`. Requiere añadir una función local de reconocimiento del pin o el equivalente mostrado:

```go
for _, pin := range PinnedPackages() {
    if d.Name == pin.Name {
        d.Latest = pin.Version
    }
}
d.Update, d.Manual = p.Update, p.Manual
if cur := liveVersion(p); cur != "" {
    d.Current = cur
}
if d.Outdated() {
    out = append(out, d)
}
```

Esto **no basta** si se mantiene `for _, d := range DepsStatus(cachePath)`: el recorrido debe partir de `c.Deps` sin filtrar. Mantener el orden preferente de `pi-gomemory` y el tratamiento explícito de errores de H-04.
- **Validación del cierre:** H-01 debe pasar con cache antigua vigente y caducada; probar también pin CC Extensions, versión local ya actualizada, caché con objetivo superior al aprobado y comandos ajenos. Comprobar que se ofrece exactamente la fuente compilada.

#### H-02 — Un enlace creado durante la confirmación se elimina

- **Categoría:** Integridad / concurrencia del sistema de archivos.
- **Severidad:** Media.
- **Estado:** CONFIRMADO ADM y ACR.
- **Ubicación:** `pkg/installer/uninstall.go:783-809`, especialmente acción en `800-809`.
- **Ruta de alcance:** `uninstall --packages` → `BuildUninstallPlan` → `planPackages` → `planCCExtensions` → confirmación → ejecución de acción.
- **Análisis:** al planificar se preservan enlaces existentes. Si un archivo por defecto se reemplaza por un enlace durante la espera, la acción sigue el enlace con `ReadFile`, compara el contenido y elimina la ruta con `os.Remove`. Se borra el enlace, **no el archivo destino**. Es una variante de revalidación no cubierta por el caso normal de enlaces ya presentes al planificar; no se ha probado que sea una regresión introducida por el diff actual.
- **Evidencia:** `TestACRADM02PreserveSymlinkAfterPlan`: acción devuelve `nil`; `Lstat` posterior devuelve `no such file or directory`.
- **Código corregido propuesto:** al comienzo de la acción, antes de `ReadFile`, revalidar tipo de entrada y conservar el enlace sobrevenido:

```go
st, err := os.Lstat(cfg)
if err != nil {
    return goneOr(err)
}
if !st.Mode().IsRegular() {
    return errChangedAfterPlan
}
```

Esto cubre el cambio **anterior al inicio de la acción**, que es el escenario reproducido. No elimina por sí solo todas las carreras entre esta comprobación y `Remove`; no presentarlo como garantía contra un actor local que sustituya entradas concurrentemente en cada operación. Un contrato más fuerte requiere diseñar la operación de retirada y su sincronización de forma explícita.
- **Validación del cierre:** H-02 debe pasar; conservar enlaces originales y sobrevenidos, rechazar directorios y enlaces rotos, y seguir retirando archivos regulares predeterminados. El destino personal debe permanecer intacto.

#### H-03 — Los probes interpretan errores como versiones válidas

- **Categoría:** Éxito falso / manejo de errores.
- **Severidad:** Media.
- **Estado:** CONFIRMADO ADM y ACR.
- **Ubicación:** `pkg/installer/deps.go:102-112`, `runOutput`; consumidores `versionFromCmd` y `latestFromCmd`.
- **Ruta de alcance:** `deps-refresh` → `RefreshDeps` → probes de `DefaultDepProbes` → `runOutput`. Ejemplos reales: `pi --version`, `mem version`, `mem update -check`, `codegraph upgrade --check`.
- **Análisis:** solo se devuelve el error si la salida está vacía. `CombinedOutput` combina stdout/stderr: un fallo con una versión en el diagnóstico puede producir un estado aparentemente correcto. También se puede ocultar una cancelación si ya había salida. La reproducción usa un comando sintético y no afirma que alguna herramienta externa falle hoy de esa manera.
- **Evidencia:** `TestACRADM03FailedCommandIsNotVersion`: `sh -c "printf '9.0.0\\n'; exit 7"` termina aceptado como `version="9.0.0" error=nil`.
- **Código corregido propuesto:** reemplazar el tratamiento del resultado de `CombinedOutput` en `runOutput`:

```go
out, err := cmd.CombinedOutput()
if err != nil {
    return "", err
}
return string(out), nil
```

Si un probe tiene un contrato documentado de código no cero para un resultado válido, manejarlo específicamente allí, no aceptar cualquier fallo en el helper compartido. No incluir salida sensible del proceso en el nuevo error.
- **Validación del cierre:** H-03 debe pasar; añadir fallo con stderr semver, cancelación tras salida y comando exitoso. Verificar contratos reales de cada comando de comprobación antes de endurecer el helper.

#### H-04 — Ausencia de caché se presenta como estado saludable

- **Categoría:** Éxito falso / diagnóstico.
- **Severidad:** Media.
- **Estado:** CONFIRMADO ADM; SUSPECT ACR, sin corroboración independiente B.
- **Ubicación:** `pkg/installer/deps.go:349-357,413-418`.
- **Ruta de alcance:** CLI `deps-update` → `RunDepsUpdate` → `DepsStatusFor` → `DepsStatus`.
- **Análisis:** errores de lectura/JSON se convierten en lista vacía, indistinguible de ausencia de actualizaciones. `RunDepsUpdate` devuelve cero e imprime «están al día». También se filtran entradas con `Error`; no constituyen prueba de estar actualizadas. No obliga a lanzar red implícitamente: puede fallar de forma informativa y pedir `deps-refresh`, respetando la desactivación automática.
- **Evidencia:** `TestACRADM04MissingCacheIsNotHealthy`: caché ausente → `rc=0`, stdout `✓ El meta-harness y sus dependencias están al día.`. Las variantes ilegible/JSON inválido se sostienen por lectura estática, no se ejecutaron en esta prueba.
- **Código corregido propuesto:** precondición en `RunDepsUpdate`, antes de consultar `DepsStatusFor`, usando `os`, `json`, `fmt` ya importados:

```go
data, err := os.ReadFile(cachePath)
var c depsCache
if err != nil || json.Unmarshal(data, &c) != nil || c.CheckedAt.IsZero() {
    fmt.Fprintln(stderr, "No se conoce el estado de las dependencias; ejecuta deps-refresh.")
    return 1
}
for _, d := range c.Deps {
    if d.Error != "" {
        fmt.Fprintf(stderr, "%s: estado desconocido; ejecuta deps-refresh.\n", d.Name)
        return 1
    }
}
```

Este guard es una opción conservadora. Definir además cómo tratar una lista vacía o incompleta respecto de los probes, y si se permiten actualizaciones parciales conocidas en vez de abortar todas. No declarar «al día» sin cobertura suficiente.
- **Validación del cierre:** H-04 debe pasar; cubrir JSON inválido, permisos, caché parcial, error de probe, ausencia de red y configuración de comprobaciones desactivada. Mantener éxito para una caché completa realmente al día.

#### H-05 — El límite de extracción no cubre entradas sin contenido

- **Categoría:** Fuga/agotamiento de recursos.
- **Severidad:** Media, condicionado a un tarball adverso o defectuoso del candidato solicitado.
- **Estado:** CONFIRMADO ADM por estructura; SUSPECT ACR, solo B. No se ejecutó agotamiento real.
- **Ubicación:** `pkg/installer/pins_candidate.go:238-278`, `extractCandidate`.
- **Ruta de alcance:** `PINS_CANDIDATE=… go test -tags pins … TestPinsValidate` → `validateCandidate` → tarball de npm → verificación de integridad → `extractCandidate`.
- **Análisis:** el hash verifica integridad respecto del registro, no seguridad del contenido. El límite de descarga acota bytes comprimidos y `total` solo suma `h.Size` de archivos regulares. Entradas vacías y directorios no consumen ese presupuesto: muchas entradas pequeñas pueden agotar metadatos/inodos y trabajo de CPU. No hay contexto en esta función para cancelar la extracción. El borde es una operación explícita de mantenimiento, no un endpoint remoto abierto.
- **Evidencia:** muestra sintética de **12.116 bytes comprimidos**, payload total cero, crea **2.000 archivos** y devuelve `nil`. Esta muestra es segura y **no demuestra que 2.000 sea un umbral peligroso**: la ausencia de un contador/límite explícito se demuestra por código. El test H-05 pasa como testigo del comportamiento, no como prueba de que ya se produjo un DoS.
- **Código corregido propuesto:** sustituir la construcción del lector tar por un lector limitado y añadir contador antes de procesar cada cabecera; los valores siguientes son una política inicial que debe contrastarse con los paquetes reales:

```go
const maxCandidateEntries = 10_000
const maxCandidateTarBytes = int64(256 << 20)
bounded := &io.LimitedReader{R: gz, N: maxCandidateTarBytes + 1}
tr := tar.NewReader(bounded)
entries := 0
```

Tras `h, err := tr.Next()` y **antes** del retorno por EOF:

```go
if bounded.N <= 0 {
    return fmt.Errorf("tarball descomprimido supera %d bytes", maxCandidateTarBytes)
}
```

Después del manejo de EOF/error y antes de crear rutas:

```go
entries++
if entries > maxCandidateEntries {
    return fmt.Errorf("tarball supera %d entradas", maxCandidateEntries)
}
```

Mantener el límite de payload existente y la limpieza temporal en fallo. Para cancelación, pasar `context.Context` a la extracción y comprobarlo entre entradas, sin afirmar que el timeout HTTP cubre esta fase.
- **Validación del cierre:** fixture de `maxCandidateEntries+1` entradas vacías y otro de directorios; cabeceras extendidas voluminosas; cancelación; limpieza tras error; conservar éxito con ambos tarballs reales. La muestra de 2.000 por sí sola **no debe** convertirse en test que exija rechazo arbitrario.

## 3. Recomendaciones de resiliencia

1. Priorizar H-01 por impacto en el cambio de pins en curso, H-02 por preservación de configuración y H-03 por fiabilidad transversal de probes. H-04 y H-05 conservan identidad separada; no confundir evidencia ADM con consenso ACR.
2. Integrar los cuatro escenarios de regresión como pruebas permanentes, después de acordar el comportamiento esperado. Añadir límites explícitos de entradas/descompresión para H-05, con fixtures pequeños que crucen el umbral configurado.
3. Incorporar análisis de vulnerabilidades y Shell cuando esas herramientas estén disponibles en un entorno de CI controlado. La ausencia local de herramientas no debe transformarse en resultado verde ficticio.
4. Separar «no hay actualizaciones conocidas» de «se verificó que todo está al día»; separar datos de versión de errores y de comandos autorizados.
5. Mantener comprobaciones npm reales sin caché en release, pero no interpretar contratos textuales como garantía de semántica, UI o compatibilidad completa de upstream.
