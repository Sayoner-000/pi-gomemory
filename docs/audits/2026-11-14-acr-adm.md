### H-01 — El fallo parcial elimina la información necesaria para reintentar

- **Categoría:** integridad / recuperación de fallos.
- **Ubicación:** `pkg/installer/uninstall.go:594-600,654-656,860-898`.
- **Ruta:** CLI `uninstall --yes` → `Uninstall` → `BuildUninstallPlan` → retirada de launcher y manifiesto.
- **Causa:** el manifiesto se planifica como archivo ordinario y se borra aunque antes haya fallado otra acción. Guarda el BIN_DIR y las huellas de la instalación, no solo una caché prescindible.
- **Impacto:** tras un fallo de permisos queda el launcher, pero desaparece la referencia a su directorio personalizado; el reintento puede dejar de localizarlo. Las huellas de versiones anteriores también se pierden.
- **Evidencia:** `TestADMManifestSurvivesFailure` crea un launcher y manifiesto sintéticos, aplica modo `0555` al directorio y ejecuta `Uninstall`. La salida muestra una retirada fallida por permisos y la retirada efectiva del manifiesto. El contrato falla con `H-01: failed uninstall removed recovery manifest`.
- **Cierre mínimo:** retirar el manifiesto solo tras completar sin fallos todas las acciones, incluidas `--packages` y `--self`; mantenerlo ante fallos. Conservar la representación de la acción en dry-run.
- **Código propuesto, no aplicado:** condición en la fase final, después de extraer la retirada del manifiesto del bucle genérico:

```go
if counts[ActionFail] == 0 {
    if err := os.Remove(ManifestPath(opts.HomeDir)); err != nil && !isAbsent(err) {
        return fmt.Errorf("retirar manifiesto: %w", err)
    }
}
```

El fragmento requiere integrar el conteo y la impresión del plan; no es un parche autónomo. **Validación del cierre:** el test negativo debe pasar; añadir reintento tras restaurar permisos y caso de fallo en `--packages` para asegurar que el manifiesto se retira realmente al final.

### H-02 — La edición rompe configuraciones gestionadas mediante symlinks

- **Categoría:** integridad / configuración.
- **Ubicación:** `pkg/installer/jsonfile.go:35-50,67-88`; rutas de desinstalación en `pkg/installer/uninstall.go:365-384,479-511`.
- **Ruta:** CLI `mcp` o `install` → `InstallMCPServers` → `writeJSONObject` → `writeFileAtomic`; también editores de settings/AGENTS durante uninstall.
- **Causa:** la lectura y `Stat` siguen el enlace, pero `Rename(temp, path)` reemplaza el enlace, no el archivo al que apuntaba.
- **Impacto:** Pi queda desacoplado del archivo gestionado en dotfiles; ese destino no recibe la edición. No se ha demostrado fuga de credenciales.
- **Evidencia:** `TestADMSymlinkRemainsManaged` enlaza `mcp.json` a un archivo sintético, ejecuta `InstallMCPServers` y comprueba con `Lstat` que el enlace se convirtió en archivo regular. El destino conserva su JSON original.
- **Cierre mínimo:** definir y aplicar una política explícita. La opción defensiva más acotada es rechazar enlaces sin tocar ninguno de los archivos. Resolver y editar el destino sería otra política, que requiere validar rutas y permisos.
- **Código propuesto:** al inicio de `writeFileAtomic`, antes de crear temporales:

```go
info, err := os.Lstat(path)
if err != nil && !errors.Is(err, fs.ErrNotExist) {
    return err
}
if err == nil && info.Mode()&os.ModeSymlink != 0 {
    return fmt.Errorf("no se modifica una configuración enlazada: %s", path)
}
```

**Validación del cierre:** con la política de rechazo, adaptar el test para esperar error explícito y ambos archivos intactos; cubrir settings, MCP, AGENTS y enlace colgante. No dar por resueltas carreras de sustitución concurrente solo con este control.

### H-03 — Se cancela la escalada antes de matar al descendiente

- **Categoría:** fuga de recursos / ciclo de vida de procesos.
- **Ubicación:** `extensions/gomemory-tdd.ts:552-560,600-604`.
- **Ruta:** `/tdd run` o `run_tdd_tests` → ejecución de suite → `runCheck` → `streamLines` → abort/timeout.
- **Causa:** se envía SIGTERM al grupo y se programa SIGKILL a los 800 ms, pero el `close` del hijo directo elimina ese temporizador. Un descendiente resistente que no mantenga las tuberías del padre abiertas sobrevive.
- **Impacto:** procesos de prueba huérfanos que consumen recursos o mantienen servicios/puertos después de cancelar.
- **Evidencia:** `TestADMResistantDetachedStdioDescendant` espera por IPC a que el descendiente haya instalado su manejador de SIGTERM, cancela, espera 1500 ms y sigue pudiendo señalizar ese PID. Falla con `resistant descendant remains alive`. La reproducción mata el PID en `finally`.
- **Cierre mínimo y código propuesto:** no cancelar la escalada por el cierre temprano del hijo cuando hubo terminación solicitada:

```ts
if (timeoutTimer) clearTimeout(timeoutTimer);
if (killTimer && !terminated) clearTimeout(killTimer);
```

Debe mantenerse el temporizador programado para el grupo y comprobarse el comportamiento al resolver la promesa. **Validación del cierre:** el test nuevo y `TestHCD027ProcessGroupCleanup` deben pasar; cubrir tanto abort como timeout y comprobar que no se señaliza al anfitrión.

### H-04 — El instalador hijo olvida el BIN_DIR de la instalación

- **Categoría:** integridad de configuración / actualización.
- **Ubicación:** `main.go:227-230`, `pkg/installer/installer.go:26-33,80-86`.
- **Ruta:** instalación con `PI_GOMEMORY_BIN_DIR=/ruta/custom`; en otra shell sin esa variable, `/ruta/custom/pi-gomemory-setup update` → reemplazo del ejecutable → `exec.Command(exe, "install")`.
- **Causa:** el hijo hereda el entorno, pero no recibe el BIN_DIR guardado en el manifiesto. `DefaultOptions` selecciona `~/.local/bin` y el manifiesto se reescribe con ese directorio.
- **Impacto:** launcher duplicado o antiguo en el directorio original; una desinstalación posterior puede omitirlo como ajeno y `--self` no coincidir con el nuevo BIN_DIR registrado.
- **Evidencia:** `TestADMCustomBinDirRetainedByChildInstall` escribe el manifiesto sintético, elimina el override y ejecuta el mismo cálculo `DefaultOptions` que realiza el hijo. Obtiene `~/.local/bin`, no el directorio registrado. La continuidad hasta launcher/manifiesto se verifica en `InstallAll`. **No es una prueba E2E de descarga y actualización.**
- **Cierre mínimo:** antes de relanzar, recuperar el directorio establecido, respetando el override explícito si esa es la política acordada. No ignorar un manifiesto ilegible.
- **Código propuesto**, antes de `cmd.Run()`:

```go
binDir := opts.LocalBinDir
m, err := installer.ReadManifest(opts.HomeDir)
if err != nil {
    return fmt.Errorf("leer instalación antes de reinstalar: %w", err)
}
if os.Getenv("PI_GOMEMORY_BIN_DIR") == "" && m != nil && m.BinDir != "" {
    binDir = m.BinDir
}
cmd.Env = append(os.Environ(), "PI_GOMEMORY_BIN_DIR="+binDir)
```

**Validación del cierre:** probar el relanzamiento real con servidor local y ejecutable temporal, sin sustituir el binario del harness; comprobar manifiesto y launcher en custom, ausencia de launcher en default y uninstall posterior. Decidir también qué hacer si no existe manifiesto.

### H-05 — «Al día» sin haber comprobado actualizaciones

- **Categoría:** éxito falso.
- **Ubicación:** `main.go:206-214`, `pkg/installer/update.go:108-124`.
- **Ruta:** `PI_GOMEMORY_NO_UPDATE_CHECK=1 pi-gomemory-setup update`.
- **Causa:** `CheckUpdate` devuelve `Newer=false` y `Err=nil` al desactivar la comprobación; `runUpdate` interpreta ese resultado como versión actualizada.
- **Impacto:** diagnóstico engañoso y actualización explícita omitida. No se necesita afirmar que había una release nueva para demostrar que la conclusión «al día» carece de comprobación.
- **Evidencia:** binario compilado con `-X main.version=v0.0.1` imprime `✓ pi-gomemory-setup ya está al día (v0.0.1).` y sale con 0 al activar esa variable.
- **Cierre mínimo y código propuesto:** si se mantiene el bloqueo para la actualización explícita, informar del bloqueo en vez de éxito:

```go
if installer.UpdateCheckDisabled() {
    return fmt.Errorf("comprobación de actualizaciones desactivada; no se determinó si hay una versión nueva")
}
```

Alternativa: separar comprobación pasiva de actualización explícita y permitir esta última. **Validación del cierre:** entorno desactivado nunca debe producir «al día» sin consulta; añadir un servidor local y verificar el comportamiento elegido.
